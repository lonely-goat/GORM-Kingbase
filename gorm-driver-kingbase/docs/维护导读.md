# 维护导读：以后从这里继续

本文供后续开发和交接使用，目录、调用关系、修改入口及测试命令均记录在仓库中，不依赖此前的聊天记录。本文的相对路径以本文件所在位置为准；命令统一在整个 Git 仓库的根目录执行。

## 先确认自己打开了正确的仓库

```sh
git rev-parse --show-toplevel
git status --short --branch
git remote -v
```

正式开发分支是 `kingbase-driver`，远程为 `https://github.com/lonely-goat/GORM-Kingbase.git`。整个仓库根目录同时包含 `README.md`、`scripts/`、`gorm-driver-kingbase/` 和 `third_party/`。不要把只含适配器源码的子目录误当成完整交付仓库。

在最初的开发电脑上，这个 Git 工作目录暂时位于外层工作区的 `deliverables/GORM-Kingbase-delivery-2026-11-02/`。这个路径只是当时整理时的选择，不是运行要求。若在其他电脑克隆仓库，以 `git rev-parse --show-toplevel` 的实际输出为准；若以后移动整个 Git 工作目录，保留 `.git` 及源码相对位置即可。

外层工作区还保留旧的适配器副本、GORM 研究仓库、历史日志和压缩包。它们与本 Git 工作目录不自动同步。本机各副本的位置以外层工作区的 `开始阅读.md`、`WORKSPACE.md` 为准；这两个本机说明不属于公开仓库的运行依赖。

## 两个分支与运行依赖

| 项目 | 用途 |
|---|---|
| `master` 分支 | Fork 下来的 GORM 核心快照，保留作研究对照；不会自动更新到官方最新版本 |
| `kingbase-driver` 分支 | 当前交付和维护的适配器、SDK、测试及文档；是默认分支 |
| [适配器 go.mod](../go.mod) | 固定依赖 `gorm.io/gorm v1.31.1`，通过相对路径引用配套 gokb |
| [third_party/gokb](../../third_party/gokb) | 实际使用的配套 `kingbase.com/gokb` 源码，保留原版权与原始文件 |
| [GORM 测试基线](../testdata/upstream/gorm-v1.31.1.tar.gz) | 官方固定版本源码归档，供脚本解压到临时目录跑回归 |

运行关系：业务或测试程序 → GORM 与金仓 Dialector → `database/sql` → gokb → 金仓数据库实例。运行时 GORM 来自 Go 模块依赖，不会读取 `master` 分支，也不依赖开发电脑的 Go 缓存目录路径。

当前方式支持下载整棵源码树后构建、测试。作为另一个业务模块的依赖使用时，需要配置适配器和 gokb 的本地替换，见[开发说明](development.md)。不要把当前交付方式当成已经完成公开 `go get` 模块发布。

| 两种模式字段类型 | [mysql_types.go](../mysql_types.go)、[oracle_types.go](../oracle_types.go) | 整数、字符串、时间、数值和自增字段映射 |

## 测试入口不要混淆

| 根目录命令 | 作用与前提 |
|---|---|
| `bash scripts/test.sh` | 构建、无数据库测试、vet；会清除自身进程里的 DSN，实库场景跳过 |
| `bash scripts/test.sh race` | 无数据库竞态检测，需要 CGO 和 C 编译器 |
| `bash scripts/test.sh integration` | 真正连接两种模式的金仓实例；要求两条 DSN 和 `KINGBASE_TEST_ALLOW_DDL=yes` |
| `bash scripts/test.sh official-mysql` | 固定版本 GORM 的 MySQL 模式回归，需要对应 DSN、DDL 开关、Python 3.9+ 和 patch |
| `bash scripts/test.sh official-oracle` | 固定版本 GORM 的 Oracle 模式回归，前提同上 |

实库测试使用 `KINGBASE_MYSQL_DSN`、`KINGBASE_ORACLE_DSN`，格式和实例设置见[根目录 README](../../README.md)及[测试说明](testing.md)。测试会创建、修改和删除对象，应连接专用测试数据库；凭据保留在本机环境中。

无数据库命令成功、集成包显示 `ok` 或用例显示 `SKIP`，都不能代替实库通过。官方回归脚本会对临时测试副本应用方言接入和断言补丁，报告结果时要保留这一说明。

## 一次正常修改如何提交

1. 先确认 Git 根目录及分支，查看 `git status`。工作树干净时再用 `git pull --ff-only` 取得远程更新；已有未提交修改时先整理自己的修改。
2. 修改对应生产文件；修复行为时，在无数据库测试或 `integration/` 中补上能够发现问题的回归用例。
3. 执行相关测试。只有注释、说明文档发生变化时，核对文档链接和差异即可，不把旧实库结果写成新结果。
4. 用 `git diff` 检查本次改动，按实际文件路径执行 `git add`，然后 `git commit`。
5. 用 `git push origin kingbase-driver` 更新当前开发分支；普通 GitHub 登录或凭据仍需在当前电脑上可用。

`manifest.json` 是交付文件的摘要清单。源码或文档修改后，旧压缩包不会自动更新；下一次交付应重新打包。记录中的构建、单元及竞态结果应注明验证对应的源码；仅更新文档时，不宣称已重新执行实库验证。

## 生成下一份交付包

从本 Git 工作目录的根目录运行，使用尚不存在的输出名称：

```sh
python3 gorm-driver-kingbase/scripts/build-review-bundle.py deliverables/GORM-Kingbase-review-next --race
```

脚本会生成目录、ZIP、tar.gz、摘要及验证记录，校验 SDK 来源摘要和文档链接，并在禁止模块网络下载的环境中构建、测试；普通依赖需要先下载到本机 Go 缓存。详细选项见[开发说明](development.md)。

`deliverables` 的常规用途是存放这些交付产物。打包脚本不会创建 Git 仓库，也不会让新包自动成为开发目录；后续开发继续在原 Git 工作目录进行。历史压缩包和日志保留原样，不能认为它们始终对应当前分支最新提交。

## 后续维护边界

- 日常适配修改在本项目完成，不直接改 Go 模块缓存里的 GORM/MySQL/Oracle 对照源码。
- 更新 GORM 版本时，同步更新固定测试基线及补丁，再跑相应回归；不要只改 `go.mod` 的版本号。
- 更新配套 gokb 时，保留版权和来源记录，重新生成 [SDK 文件摘要](../../third_party/gokb-source.json)，并验证两种模式；不要随意改写供应商源码注释或版本。
- 当前 `kingbase-driver` 是交付目录结构，直接向 GORM 核心提交整个分支会包含删除原核心文件的差异。核心贡献应从上游另建最小改动分支；社区项目收录可按 [GORM 社区页](https://gorm.io/community.html) 的入口提交介绍和链接。
